## 二、★ 三处与规格冲突的地方 ★

### 冲突 1：配置用 JSON，规格要求 ScriptableObject ✗

| | |
|---|---|
| **规格** | "优先使用 ScriptableObject 保存静态配置，避免将玩家运行时状态写入共享配置资产" |
| **现状** | `TableDatabase` 从 `Resources/Data/*.json` 反序列化到 `Defs.cs` 里的 POCO ✓ |
| **为什么这是冲突** | SO 是**资产 + 编辑器可视化** ✓ JSON 是**文本 + 可脚本化** ✓ 两者都能"静态配置与运行时分离" ✓ 但迁移全部 5 张表到 SO 是**大工程** ✗ |

**冲突的本质**：规格想要的是**那个好处**（静态/运行时分离、编辑器可编辑）✗
而现状**已经满足了"分离"** ✓：

```
静态：Defs 里的 SeedDef / ItemDef / ToolUpgradeDef（只读，从表载入）
运行时：SeedSlot / PlantAlly / StatBlock / Progress（持有实例状态）✓ 已经分开了 ✓
```

**最小修改方案（我建议）**：
1. **不迁移现有 5 张表** ✓ —— 它们工作正常且有 319 条断言覆盖 ✗ 迁移会让全部断言失效 ✓
2. **新增的三类数据（插件 / 新版种子 / 道具）用 SO** ✓ —— 规格要求的是"新的商品体系"，正好可以从一开始就用 SO ✓
3. **保留 `TableDatabase` 作为载入入口** ✓ —— 让它同时支持 JSON 与 SO 两种来源，调用方无感 ✓

**这样既满足规格的好处，又不动已验证的部分** ✓

### 冲突 2：`RunSession.cs` 是 2786 行的上帝类 ✗

它现在同时持有：阶段机、回合推进、刷怪、商店、农场、水壶激光、弹字、商店车、Boss 表、暂停 ✗

**规格要求**："不要把每种商品复制一套独立逻辑"、"明确的接口"、"不为了设计模式过度抽象" ✓

**最小修改方案**：**不拆分**，而是**新增的子系统都做成独立类**，由 `RunSession` 持有引用 ✓

```
RunSession（保持为"会话门面"）
  ├─ Clock / BossSchedule / ShopTruck      ← 已经是独立类 ✓ 这个模式有效 ✓
  ├─ WeaponSystem（新）                     ← 阶段 3
  ├─ PluginSystem（新）                     ← 阶段 3
  ├─ ItemEffectSystem（新）                 ← 阶段 4
  └─ ShopPool（新）                         ← 阶段 5
```

**判据**：新代码不再往 `RunSession` 里堆 ✗ 而 `RunSession` 只做**转发与生命周期** ✓
**这比"先把 2786 行拆成 10 个文件"安全得多** ✗（后者会让 319 条断言大面积失效 ✓）

### 冲突 3：没有 Animator，动画靠 `SampleAnimation` 手驱 ✗

```
ModelView.cs: 用 AnimationClip.SampleAnimation 手驱，不挂 Animator
```
